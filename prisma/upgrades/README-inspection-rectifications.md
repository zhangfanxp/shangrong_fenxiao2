# 巡检整改

迁移：`202610161500_add_inspection_rectifications.sql`，数据库版本 47。

通过正常的 `npm run deploy:migrations` 部署。迁移创建整改及轮次表，将通知正文扩展为 LONGTEXT，并为已有巡检提交权限的角色补充巡检整改的查看、发起、无需整改和验收权限。新增角色可在角色管理中分别配置这些权限。

## 数据和状态

- 只有功能上线后正式提交的巡检才生成待处理问题，不回填历史巡检。前厅、后厨、信用评分均适用。
- 同一巡检按检查表顺序，对不合格和部分合格项共同连续编号：原巡检编号加 `_001`、`_002`。每个问题只有一个固定编号，返工继续使用原编号。
- 所有运营列表、详情和操作都限定为原巡检人本人，即使具有管理员权限也不能读取他人的整改记录。
- 状态：待生成 → 整改中 → 待验收 → 整改合格；验收不合格返回整改中并创建新轮次、新任务。待生成可标记无需整改，原因选填，不可恢复。
- 发起后，每轮要求、责任人、抄送、照片、说明、提交及验收时间均保留。原巡检得分不变，原巡检不可删除。PC任务记录中关联的整改证据也不能直接编辑或删除。

## 责任人、期限和照片

首次发起：前厅和信用评分固定为当前店长，后厨固定为当前厨师长。默认人缺失、停用或无法执行门店任务时，才开放本店其他有效人员选择。候选人须能登录门店H5，并有任务查询、查看、上传和提交权限；同时遵守品牌访问范围。验收退回默认沿用上一轮责任人和期限，可重新选择。

期限为发起时刻加24、72或168小时，界面同时显示北京时间的具体截止时间。整改中实时判断超时，提交后按本轮提交时间固定超时结果，验收等待不计入。每轮的生成时间、截止时间、提交时间均可用于后续统计。

整改任务超时后仍在待完成列表中，可以上传、暂存和提交；普通任务的截止规则不变。整改照片必须1～5张，整改说明选填；原巡检照片和整改照片分别展示。整改任务沿用现有临时任务的完成率默认设置，后续超时率可按整改轮次单独统计。

照片使用巡检表当前配置的R2存储空间，在任务创建时保存空间快照并登记业务引用。存储空间缺失或不可用时，发起失败并给出提示。

## 通知

默认抄送门店区域负责人，以及有效的运营总监、运营助理、总经理角色用户；按用户去重。默认与手选人员合计最多10人，默认超过10人时须手动调整，不自动截断。

- 发起整改：立即通知本轮抄送人。
- 验收合格：通知本轮责任人和抄送人。
- 验收不合格：发送一次验收退回通知，包含新一轮要求，通知前后轮次的相关责任人、抄送人，收件人去重。
- 门店提交整改、标记无需整改不发送通知。通知包含完整文字字段，不包含图片；人工发布普通通知的500字符校验仍保留。

## 验证

运行与本工作目录使用同一数据库、配置目录的本地测试服务，再执行：

```sh
RECTIFICATION_VERIFY_URL=http://127.0.0.1:3002 npm run verify:inspection-rectifications
```

验证脚本创建专用账号、品牌、门店、巡检模板及本地S3测试服务，实际经过签名、PUT、上传确认和任务提交。覆盖编号、历史不回填、本人范围及操作权限、三类默认责任人、默认人缺失回退、并发发起、照片数量、超时提交、多轮退回改派、通知时机、原分数及删除保护。测试消息仅发送给测试账号，结束后清理测试业务数据和配置文件。
